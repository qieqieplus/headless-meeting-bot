# 视频编码模块设计文档

## 概述

视频模块负责将 Zoom SDK 提供的原始音视频数据编码为 HLS (HTTP Live Streaming) 格式，支持实时流式传输。模块采用管道式架构，通过 FFmpeg 实现硬件/软件编码、多路复用和内存输出。

## 顶层架构

### 核心组件

```
MediaEncodePipeline (协调器)
├── VideoEncoder (H.264 编码)
├── AudioEncoder (AAC 编码)
├── HlsMuxer (HLS 多路复用)
└── AvioMemorySink (内存输出)
```

### 数据流

```
原始数据输入 (I420/PCM)
    ↓
帧队列 (环形缓冲区)
    ↓
Worker 线程处理
    ↓
编码器 (H.264/AAC)
    ↓
多路复用器 (fMP4 段)
    ↓
内存输出 (回调)
```

## 模块设计

### 1. MediaEncodePipeline

**职责**：协调整个编码管道，管理线程和队列

**设计要点**：
- **生产者-消费者模式**：外部线程推送帧，内部 worker 线程处理编码
- **环形缓冲区**：固定大小池（视频 4 帧，音频 8 帧），避免动态分配
- **非阻塞推送**：队列满时丢弃新帧，保证实时性
- **延迟初始化**：编码器在收到第一帧时初始化，支持动态分辨率

**关键实现**：
- 使用 `condition_variable` 实现高效等待（有数据或关闭信号时唤醒）
- 单锁保护两个队列，减少锁竞争
- 停止时刷新编码器缓冲区，确保所有数据被输出

### 2. VideoEncoder

**职责**：H.264 视频编码

**设计要点**：
- **多编码器支持**：自动选择 x264（软件）或 nvenc（硬件）
- **动态重初始化**：分辨率变化时重新配置编码器
- **包队列管理**：编码可能产生 0/1/多个包，内部队列缓冲
- **关键帧控制**：支持按需请求 IDR 帧

**关键实现**：
- 使用 FFmpeg 的 `AVCodecContext` 管理编码器生命周期
- 时间戳单位转换：输入毫秒 → 编码器微秒
- 自动填充包持续时间（duration），确保时间基正确

### 3. AudioEncoder

**职责**：AAC 音频编码

**设计要点**：
- **重采样支持**：处理不同采样率和声道配置
- **FIFO 缓冲**：使用 `AVAudioFifo` 管理变长 PCM 输入
- **PTS 对齐**：维护连续的时间戳序列，避免音频跳跃
- **延迟初始化**：等待视频编码器初始化后再配置

**关键实现**：
- 使用 `SwrContext` 进行重采样（支持采样率和声道转换）
- FIFO 确保每次编码输入固定帧大小（AAC 要求）
- 时间戳以采样点为单位，与编码器时间基对齐

### 4. HlsMuxer

**职责**：HLS 多路复用，生成 fMP4 段和播放列表

**设计要点**：
- **fMP4 格式**：使用分段 MP4，支持更好的流式传输
- **内存输出**：通过自定义 AVIO 回调，不写磁盘
- **严格初始化顺序**：必须先配置视频流，再配置音频流
- **播放列表管理**：自动更新 `.m3u8`，支持 VOD/Live/Event 模式

**关键实现**：
- 使用 FFmpeg 的 HLS muxer，配置 `hls_segment_type=fmp4`
- 时间基由 FFmpeg 自动选择，避免手动计算错误
- 通过 `independent_segments+append_list` 标志优化播放列表更新

### 5. AvioMemorySink

**职责**：内存输出管理，文件回调分发

**设计要点**：
- **自定义 AVIO**：拦截 FFmpeg 的文件操作，重定向到内存
- **文件生命周期**：跟踪每个文件的打开/关闭，触发回调
- **播放列表缓存**：记录最后播放列表内容，支持结束标记注入

**关键实现**：
- 使用 `AVFormatContext::io_open/io_close2` 钩子
- 每个文件对应一个 `FileBuffer`，通过 `AVIOContext*` 映射
- 支持 seek 操作（FFmpeg 需要查询文件大小）

## 关键实现细节

### 初始化顺序

严格的初始化顺序确保 FFmpeg 组件正确配置：

1. **视频编码器初始化**：确定帧格式和分辨率
2. **Muxer 初始化**：创建容器，需要视频编码参数
3. **音频编码器初始化**：可独立初始化
4. **音频流配置**：将音频编码参数复制到 muxer
5. **启动 Muxer**：写入容器头部和初始化段
6. **清空队列**：丢弃初始化前的帧，避免音视频不同步

### 音视频同步策略

- **音频等待视频**：在 muxer 未就绪时丢弃音频帧，确保从第一帧开始同步
- **时间戳对齐**：视频使用微秒，音频使用毫秒，在各自编码器内转换
- **队列刷新**：启动时清空预缓冲帧，避免时间戳不连续

### 丢帧策略

- **队列满时丢帧**：保证实时性，避免内存无限增长
- **初始化前丢帧**：确保从正确的时间点开始编码
- **日志记录**：丢帧时记录警告，便于监控

### 动态分辨率处理

- **延迟初始化**：第一帧到达时确定分辨率
- **重初始化**：分辨率变化时调用 `Reinitialize`，关闭并重新打开编码器
- **状态检查**：每次编码前检查分辨率是否匹配

## 设计权衡 (Tradeoffs)

### 1. 内存 vs 延迟

**选择**：固定大小环形缓冲区（视频 4 帧，音频 8 帧）

**权衡**：
- ✅ 优点：内存占用可预测，无动态分配开销
- ❌ 缺点：队列满时丢帧，可能影响质量
- **替代方案**：动态队列会增加内存不确定性和分配开销

### 2. 同步 vs 复杂度

**选择**：音频等待视频初始化完成

**权衡**：
- ✅ 优点：简化同步逻辑，确保从开始就对齐
- ❌ 缺点：可能丢失初始音频数据
- **替代方案**：独立初始化需要更复杂的时间戳补偿机制

### 3. 灵活性 vs 性能

**选择**：支持动态分辨率变化，但需要重初始化

**权衡**：
- ✅ 优点：适应屏幕共享等场景的分辨率变化
- ❌ 缺点：重初始化有延迟，可能丢帧
- **替代方案**：固定分辨率性能更好，但灵活性受限

### 4. 内存输出 vs 文件系统

**选择**：完全内存输出，通过回调分发

**权衡**：
- ✅ 优点：无磁盘 I/O，适合容器化部署，便于网络传输
- ❌ 缺点：内存占用较高，需要及时处理回调
- **替代方案**：文件系统输出更简单，但需要管理磁盘空间

### 5. 编码器选择

**选择**：自动选择 x264/nvenc

**权衡**：
- ✅ 优点：硬件加速时性能更好，软件编码兼容性更好
- ❌ 缺点：需要运行时检测，增加复杂度
- **替代方案**：固定编码器更简单，但失去灵活性

## 性能考虑

### 线程模型

- **单 worker 线程**：避免多线程编码的同步开销
- **非阻塞推送**：外部线程不等待编码完成
- **条件变量等待**：无数据时线程休眠，减少 CPU 占用

### 内存管理

- **零拷贝优化**：帧数据在队列中移动而非复制（C++11 move）
- **预分配缓冲区**：避免编码过程中的动态分配
- **及时释放**：编码后的包立即释放，不长期持有

### 编码优化

- **批量处理**：一次编码可能产生多个包，全部处理完再等待
- **关键帧控制**：支持按需请求 IDR，减少不必要的关键帧
- **GOP 大小**：可配置，平衡延迟和压缩率

## 错误处理

- **初始化失败**：记录错误日志，返回 false，不崩溃
- **编码失败**：记录警告，继续处理下一帧
- **Muxer 写入失败**：记录错误，但继续编码（避免级联失败）
- **资源清理**：析构函数确保所有资源正确释放

## 扩展性

### 当前限制

- 固定编码格式（H.264 + AAC）
- 固定输出格式（HLS fMP4）
- 单流处理（每个 Pipeline 处理一个流）

### 可能的扩展

- **多编码格式**：VP9、AV1 等
- **多输出格式**：DASH、RTMP 等
- **多码率**：自适应码率流
- **并行编码**：多线程编码（需要更复杂的同步）

## 依赖关系

- **FFmpeg**：编码、多路复用核心库
- **libx264**：软件 H.264 编码（可选）
- **NVENC**：硬件 H.264 编码（可选，需要 NVIDIA GPU）
- **标准库**：C++11 线程、容器、智能指针

## 使用示例

```cpp
// 创建管道
auto pipeline = std::make_shared<MediaEncodePipeline>();

// 配置
VideoEncoderConfig video_cfg{...};
AudioEncoderConfig audio_cfg{...};
HlsMuxerConfig muxer_cfg{...};

// 文件回调
auto callback = [](const char* filename, const uint8_t* data, 
                   size_t size, int is_playlist, uint64_t seq) {
    // 处理文件数据
};

// 启动
pipeline->Start(video_cfg, audio_cfg, muxer_cfg, callback);

// 推送数据
pipeline->PushVideoI420(y, u, v, width, height, timestamp_ms);
pipeline->PushAudioPcm(pcm_data, pcm_length, sample_rate, channels, timestamp_ms);

// 停止
pipeline->Stop();
```

## 总结

视频模块采用管道式架构，通过清晰的模块划分和严格的初始化顺序，实现了高效、可靠的实时编码。设计在内存占用、延迟、灵活性和性能之间取得了平衡，适合实时会议场景的需求。
